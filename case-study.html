Struts 2 → Spring

Migrating 600+ routes of a live enterprise application, without a rewrite

A case study in incremental legacy modernisation — method, guardrails, and what shipped.

The skills this produced

The problem

A large, long-lived enterprise Java web application in logistics and cross-border cargo handling. Hundreds of Struts 2 .do actions, a Hibernate 3 data layer, an Ext JS front end, JSP views, and a Spring Security configuration grown over years. Real users on it every working day.

The framework was long past support and blocking every dependency upgrade behind it. The obvious answer — rewrite it — was not available: there was no second team to run the old system while a new one was built, no downtime budget, and no complete specification of what the application actually did. The behaviour was the specification, and it only existed in the code.

So the constraint was set the other way round: the application stays live and keeps behaving identically, while the framework underneath it is replaced one route at a time.

What “identical” had to mean

“Preserve behaviour” is uselessly vague until you write down what is observable. For this migration the contract was explicit, and every one of these had to survive a route move:

  • URL and HTTP method, including wildcard action patterns
  • Request parameter names and formats, down to legacy date parsers that accept six different layouts
  • Response body shape — including a legacy pseudo-JSON envelope served as text/html, quirks intact
  • Status codes on failure, and the exact escaped error payload clients parse
  • Validation messages, redirects, cookies, and locale handling
  • Session semantics and per-operation authorities
  • Side effects: what gets persisted, archived, counted, or generated

Modernising Spring itself, the Java language level, and the container is separate, later work. Folding it into the migration would make every regression ambiguous — was it the route move, or the upgrade?

The unit of work: a functional slice

The migration never moves “a controller”. It moves a route together with everything that calls it: the JSP, every Ext JS caller, any external consumer, and the tests. A route migrated without its callers is a route with two implementations and no owner.

Each slice runs in a fixed order:

  • Characterize first. Exercise the live legacy route and write down its actual contract — not what the code appears to do. Characterization tests are written before any change, so they describe the old behaviour rather than ratify the new.
  • Replace the action with a thin Spring controller delegating to services, with explicit request, response, and view models.
  • Move the clients in the same change. Struts tags, ValueStack access, and action names come out of the JSP and the JavaScript.
  • Verify, then retire. Struts mappings, filters, and JARs are removed only after both routes pass and traffic confirms the legacy path is dead.

Slices are size-capped on purpose. A slice small enough to hold in your head is a slice you can prove.

Compatibility forwards, not redirects

Old URLs cannot simply disappear — bookmarks, cached JavaScript, integrations, and clients nobody has an inventory of still call them. The usual reflex is an HTTP redirect. That is the wrong tool: a redirect can change the method, drop the body, re-run authentication, and alter the status code the caller sees. Any of those is a behaviour change wearing a compatibility costume.

Instead, a registry maps each legacy path — and, where an action multiplexed on a selector parameter, each individual operation — to an internal server-side forward reaching the same Spring-native implementation the canonical route uses. One implementation, two doors. The caller cannot tell which door it came through.

An alias stays active while any registered client is still pending, and retires on evidence — an observation window with no traffic — rather than on a date in a plan.

A migrated route must be Spring-native end to end. A Spring controller that reaches back into a Struts action bean has not migrated anything; it has added a layer. That rule is enforced by contract tests, not by good intentions.

Making progress auditable

At this scale the hard problem is not moving a route. It is knowing, six weeks later, which routes really moved, which are half-moved, and what evidence exists for either. Memory and commit messages do not survive that.

Every route has a record: legacy pattern, canonical path, compatibility mode, request contract, response contract, security, side effects, the exact client files updated, the tests that cover it, and — the field that matters most — what remains unverified.

routes:
  - id: customer-search
    legacy:    { method: POST, path: /customer/search.do }
    canonical: { method: POST, path: /rest/customers/search }
    compatibility:
      mode: server-side-alias
      legacy_route_active: true
    contract:
      breaking: false
      request_changes: none
      response_changes: none
      authentication: existing-session
    backend_status: migrated
    clients:
      - { name: customer-jsp,     status: migrated }
      - { name: reporting-client, status: pending  }

Status is a closed vocabulary, not free text, so progress cannot be inflated by adjective:

StatusMeaning
inventory-pendingKnown, not yet characterized
partially-implementedSome operations migrated, others pending
implementedSpring owns the route; ownership verified in source
implemented-verified… and focused tests cover it
implemented-live-verified… and it has been verified in a running instance
retiredThe legacy compatibility alias has been removed

A route may not sit at a terminal status while evidence is outstanding. Anything unproven stays visible in a non-terminal status or an explicit remaining field. The catalog is allowed to say the work is unfinished — that is what makes it worth reading.

Verification as a separate role

Whoever implements a slice is the worst available judge of whether it works. So acceptance is a distinct step with its own rules, run against the running application rather than the diff: focused review against project rules, the smallest useful build and test set, HTTP verification of every operation, browser end-to-end checks where UI integration matters, and persistence checks for anything that mutates state.

It returns exactly one of three outcomes, and it is forbidden from touching source code to improve its own result:

OutcomeMeaning
PASSThe migrated functionality demonstrably works from the API, client, or user perspective.
FAILIt does not. Blocking; goes back to implementation.
INCOMPLETEIt could not be verified — missing runtime access, an external system, credentials. Aliases stay, the slice stays runtime-pending.

INCOMPLETE is the load-bearing one. Without it every unverifiable check quietly becomes a pass, and the catalog turns into fiction. “We could not check this” is not “this is fine”.

Why this became a public repository

A method applied six hundred times has to live somewhere other than one person’s head. Held informally it drifts: a slice gets migrated without its callers, a status gets rounded up, a verification step gets skipped because the previous route did not need it.

So the method was written down as agent skills — structured instruction documents an AI coding agent loads when a task matches, carrying the workflow, the task modes, and the guardrails with it. The migration workflow, the quality gate, the Hibernate Criteria conversion, test design for Java and Angular, and production logging are six of them.

The application is client-owned and private. The method is not, and it generalises: the same slice-and-catalog discipline applies to any framework migration where the old system has to stay up.
